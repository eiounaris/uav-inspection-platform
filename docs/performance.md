## 3. 负载与样本

负载客户端使用 Python 标准库，采用固定 worker 数的闭环模型：每个 worker 等待自己的请求完成后再发送下一次请求。报告并发是同时活动的 worker 数，不代表固定到达率、系统最大连接数或生产峰值容量。

设备、API 和文件按独立阶段执行，不将三个阶段的样本混合。夹具始终有 5 台已配置设备，设备上报阶段分别启动 3 个和 5 个 active worker；active 表示正在发请求的设备数，不等于已配置设备数或在线缓存数。

设备拥有独立身份、稳定的 `bootId`、递增 `seq`、唯一 `eventId` 和合法执行批次。每个 worker 先进行 5 次不计入测量的预热，再无 pacing 地闭环发送进度报告；每个阶段同时满足“每 worker 至少 30 次”和“阶段至少 10 s”后结束，记录实际请求数及各 worker 计数。这是突发负载能力观测，不代表真实无人机的周期心跳频率。上报期间保持任务状态允许该操作，进度保持合法且不倒退；幂等重放不能充当新增业务吞吐。

正式测量共 11 个文件，加上预热 1 个文件，本轮预计新增 12 个版本。该矩阵用于观察串行/并行和跨分片成本，未覆盖每一大小与并发的笛卡尔积；不能据此单独推导大小与并发的独立影响。各阶段记录实际设备映射、开始/结束和完成数。每次上传使用新 `clientRequestId` 和上传会话，各 worker 按服务端返回的 `partSize`、`partCount` 传完整文件，样例生成与摘要预计算在测量外完成。

分片数量、并发上传 worker、设备上报 worker 和后台消费者数分别记录。多个文件使用同一材料要求时，说明版本顺序/锁竞争；若使用不同材料要求，记录夹具结构，保证各档可比。前一组所有版本均观察到 CONFIRMED 后再开始后一组；全部消息 DONE、Outbox SENT 和空队列在收尾核对。

每次样本保留以下单调时钟观测点：

| 观测点 | 含义 |
| --- | --- |
| `createStart` / `createResponse` | 发起创建会话请求 / 读取完整响应体 |
| `partsStart` / `partsFinished` | 发送首个分片 / 最后一个分片的成功响应体读取完毕 |
| `completeStart` / `completeResponse` | 发起完成请求 / 读完 HTTP 202 响应 |
| `versionObserved` | 首次观察到会话 COMPLETED 且存在一致的固定版本 |
| `confirmedObserved` | 首次观察到该版本链状态 CONFIRMED |

分别报告：

- 创建接口耗时：`createResponse - createStart`。
- 分片传输耗时：`partsFinished - partsStart`，不含创建会话。
- 完成接口耗时：`completeResponse - completeStart`。HTTP 202 仅表示异步请求已接收。
- 创建至定版观测耗时：`versionObserved - createStart`，包含上传、排队、定版处理、落库和轮询观测误差。
- 接收后确认观测耗时：`confirmedObserved - completeResponse`。
- 端到端确认观测耗时：`confirmedObserved - createStart`。

完成请求返回 202 后，以 250 ms 间隔轮询 COMPLETED 和 CONFIRMED，超时上限 180 s；逐文件记录每次轮询的实际计时与 HTTP 状态；业务状态用于内存内终止判断，不逐次落盘。两个首次观测点之差不能分离出精确的服务端阶段耗时；轮询间隔、HTTP 往返和客户端调度均会影响观测值。轮询请求单独计数，不充入 API 查询阶段样本。

### 3.3 有效 commit 的证据与命名

每个正式文件必须具有固定版本及正式 S3 对象，对象字节数与 SHA-256 符合预期；业务链状态为 CONFIRMED，确认交易号存在，真实 `QueryEvidence` 返回的 evidence/version/hash/org 等元组与固定版本一致。提交路径检查 `chain_attempt` 的 VALID、`validation_code=0` 和块号；若走查询恢复路径，保留 `confirmed_by` 及真实账本命中证据，不能把未知尝试改记为有效 commit。

客户端首次看到 CONFIRMED 的时间可证明业务完成的观测时刻，本文称为“有效 commit 确认观测耗时”。它包含系统排队、Gateway 调用、确认和落库、轮询等开销，不能称为 Fabric 纯 commit 延迟、出块时间或 Fabric TPS。

现有 `chain_submission`、`chain_attempt` 使用 `created_at/updated_at`，没有独立的 endorse/submit/commit 各阶段时戳。可以在同一数据库 UTC 时钟域内列出业务区间辅助值，并说明重试和后续写入会更新 `updated_at`。数据库时间不能与客户端单调时钟直接相减，DB 区间也不能替代纯 commit RPC 计时。

## 4. 资源采样

应用与 Python 客户端进程分别从 `/proc` 采集 CPU 时间、RSS、线程数、I/O 等可用字段；基础设施使用 Docker stats 采集容器 CPU、MemUsage、MemPerc 和 PID 数；本轮未采集 Docker 网络/块 I/O 吞吐。按 API、设备及文件全生命周期（包含等待后台确认）标记资源时间窗，保留原始采样与失败记录。

报告注明 CPU 百分比的分母：进程 CPU 按“一逻辑核满载为 100%”计算时，多线程值可超过 100%；Docker 的 CPU 百分比按 Docker 定义展示。另记录 CPU affinity 和 cgroup 可用核配额，不能将不同分母的百分比直接比较。进程 RSS 与容器内存统计口径不同，分别列出。

每组展示有效样本数、采样间隔、均值和采样最大值；进程 I/O 累计计数保留在原始记录，本轮不将其包装为网络吞吐。采样最大值不保证捕获两个采样点之间的峰值，短窗口采样不足须标出。若 stats 查询失败，报告为不可用及原因，不能填零。

客户端、后端和容器共用宿主机时，生成数据、HTTP 线程和采样本身也会消耗 CPU 与内存；本轮结果只适用于记录的共置拓扑，不外推独立生产集群能力。

## 5. 统计与报告格式

对成功请求按端点、设备数、并发档分别计算；文件按大小、并发档、阶段分别计算。P95 使用 nearest-rank：将 `n` 个耗时升序排列，取第 `ceil(0.95 × n)` 项。保留原始耗时，注明毫秒单位和舍入规则。不要先计算 worker P95 再平均，也不要混合不同端点或不同文件大小得到一个总 P95。

API 表应至少包含条件、请求数、成功/失败/超时、吞吐窗口、median、P95、最大值。文件表应至少包含准确字节数、并发、样本数、成功/失败及上述各阶段耗时。文件样本量较小时列出逐文件结果；本轮每组 3 或 5 个文件的 nearest-rank P95 等于该组最大值，不能据此宣称稳定的尾延迟。
