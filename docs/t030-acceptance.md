# T030 最终功能验收

本轮按 [需求第 9 节](01-requirements.md#9-验收场景) 对当前集成版本重新执行 AC-01～AC-12。历史 T001～T029 的 PASS 只用于选择工具和解释机制，不充当本轮执行证据。实际结论、日期及报告编号由 [验证记录](verification.md) 维护；T030 不包含 T031 性能测量或 T032 干净环境部署复现。

## 运行入口

使用 JDK 21，在项目根目录构建当前后端与链码。已有 Fabric 网络保持原版本、证书、账本和 CaaS 服务，不重新部署链码。停止普通后端及其他业务消费者，保留原 MySQL/Redis/Garage/RabbitMQ/Fabric 基础设施：

```bash
mvn -B -ntp -Dmaven.repo.local="$PWD/.local/m2" -f backend/pom.xml -P database-probe,fabric-probe clean verify
mvn -B -ntp -Dmaven.repo.local="$PWD/.local/m2" -f chaincode/pom.xml clean verify
python3 deploy/scripts/test_verify_final.py
python3 deploy/scripts/verify-final.py
```

脚本默认按本机 UTC+8 日期记录验收日期，也可显式使用 `--acceptance-date YYYY-MM-DD` 对齐客户端日期；各组件的实际执行 UTC 时间另行保留。总报告位于 `.local/final-acceptance/<runId>/report.json`，只有全部组件、12 项门槛及数据/产物检查通过才生成总 PASS 和 latest.json。

中断后可在生产产物未变化时执行：

```bash
python3 deploy/scripts/verify-final.py --resume .local/final-acceptance/<runId>
```

复用范围仅限该次最终矩阵中已经成功、证据文件哈希及组件工具摘要仍一致的组件，不读取旧任务的历史 PASS 冒充新结果；失败组件重新执行，失败报告保留。后端 JAR、完整生产 classes/静态资源、依赖 classpath、生产源码或链码 JAR 改变时拒绝复用，需要新矩阵。更严格的新汇总条件可以重新检查已有同矩阵原始证据，不能把缺失证据改成成功。

## 数据与证据边界

每个组件前后检查无其他项目 Java 进程及消息消费者，读取一致的二十四表原行/字段/BLOB 摘要、迁移历史和凭据摘要。所有独占夹具正常清理后要求完整业务快照恢复；最终还按初始版本集合实际读取全部原始正式对象、核对大小与 SHA-256，并对已确认版本查询双机构原登记，覆盖演示任务之外的原文件。唯一预期新增是最后原 M2 正式复查的三条核验记录，原行仍逐一保持。安全审计与真实链登记追加保留，不清库、删卷、改旧迁移或重建凭据；T029 已完成任务、文件和授权不作为负例夹具使用。

旧专项的原数据保护范围有十六至二十四表的差异，外层统一二十四表护栏用于补齐其范围。独立消息队列不能隔离同一数据库里的恢复扫描，因此启动前还要求全库在途工作静止。租约和业务扫描按各组件明示的生产/测试配置判读；真实崩溃场景等待原 120 秒租约自然到期，不写 SQL 提前过期。长读取在已打开的真实 S3 流中注入受控延迟，用于证明续租，不作为存储性能或自然下载延迟指标。

文件缺失、内容变化及链故障只作用本次对象/测试装配，成功场景由正式 API、生产处理器和真实外部服务形成。RPC 边界注入 UNAVAILABLE 证明该调用边界的故障处理，不声称共享 Fabric 网络被物理停止。链码同摘要实测会提交一笔新的 VALID 交易，但 evidence writes=0、首次 registeredTxId 保持；不能写成“完全没有新增交易”。

部分较早的跨 JVM 工具会将本次随机夹具凭据短暂保存为 0600 文件，结束必须删除；不能宣称所有组件的凭据都只在内存。总目录及报告为私有权限，末尾检查已知原凭据、JWT、PEM 私钥和原始签名 URL，保留失败日志。所有已完成组件原始报告及哈希都登记在总报告，统计按原报告的 Java HTTP、子客户端 HTTP、断言/协调器检查分别说明，不把混合计数当作压测指标。
