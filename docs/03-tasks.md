## 1. 使用方式与完成规则

- 表中依赖为必须先完成的任务；同一阶段可在依赖满足后并行，个人开发优先按编号推进。
- 每次选择一项任务，开始时更新状态，完成时记录实际产物和验证结果；遇到阻塞写明具体原因及下一步。
- 每项功能任务包括相关数据库迁移、接口、权限、必要审计及接口调用示例，避免把这些工作推到最终验收才补。
- 测试集中于权限、状态、并发、幂等和跨系统恢复；简单字段映射不单独堆叠测试。
- 若一项任务超过两个开发时段仍无法交付，可拆为保留父编号的子项，例如 T010-a、T010-b，并补充依赖和完成条件。
- 当前业务和链网络按单实例开发环境推进，不增加已排除的架构或链功能。

一项任务标记为已完成须满足：实现符合需求及设计、完成标准实际验证通过、运行方式及结果已记录、没有遗留的必做子项。探针和中间里程碑不代表完整 MVP 验收通过。

验证记录可以从首次需要时创建的 docs/verification.md 维护，至少包含任务或 AC 编号、环境版本、前置数据、操作方式、预期与实际结果、日期及必要的证据编号/交易编号。未执行的验证必须明确保留为未执行。

### 2.1 中间版本约定

- M1 是独立技术验证，不承担完整业务；不因容器启动成功就视为 Java 与 Fabric 连通验证通过。
- M2 使用最终上传会话和分片接口，先用 partCount=1 的小图片验证；不另建一次性的普通上传接口。
- M2 已包含基础异步处理、本地事务写 Outbox、必要幂等与真实链确认；租约续期、完整扫描补偿及系统性故障验证在 M4 完成。
- M2 存证超时仍须保存 UNKNOWN 及交易检查点，不能先写成失败，或伪造 CONFIRMED 让链路通过。
- 多分片、断点续传、人工复核、授权共享和全部恢复规则都是最终必交能力，不能因 M2 通过而删减。
- 人工复核和共享始终在 Java 后端执行；Fabric 保持两个组织、一个通道、一份链码和两个业务方法。
